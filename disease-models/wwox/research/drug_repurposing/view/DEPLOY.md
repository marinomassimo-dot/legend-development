## 1. What is deployed

The directory `disease-models/wwox/research/drug_repurposing/view/shareable_package/` and nothing else. It is a static site: `index.html`
is one self-contained file (inline CSS and JavaScript, data embedded as JSON, no network resource), next to `NOTICE.md`, `COMPARISON.md`,
`README.md`, `manifest.json`, `TEXT_PROVENANCE.json`, `LICENSES/` and `class_b/chembl_cc-by-sa-3.0/` (the ChEMBL records as a separate
CC BY-SA 3.0 file with its own licence text and credit). The page is Italian for the physician and is research material, not medical advice,
not a ranking of treatments and not a probability of benefit. It carries no individual-level record.

## 3. The workflow, kept as a proposal

`view/DEPLOY_pages_workflow.proposal.yml` is the whole mechanism. It has two triggers: `workflow_dispatch` and (IT19, after the operator authorised publication and updates while free) a push to `main` that changes
the package directory; it cannot run on a schedule or a pull request. The deploy step asks `configure-pages` to enable Pages if it is off (`enablement: true`; if the
workflow token is not allowed to, the run fails visibly and the one remaining operation is Settings, Pages, Source = GitHub Actions). Its first job (read-only permissions) checks that every file in the package directory, `manifest.json` included, equals the digest in the table of section 4 and in the manifest, and that no
other file is there; this is an integrity check, not a content check (the content proof is `audit-shareable --dynamic`, section 7). Its second job, the only one with `pages: write` and `id-token: write`, publishes that directory with the official Pages actions. The Pages environment normally accepts deployments only from the default branch: dispatch the workflow from that branch, after the work has landed there. It is **not** under `.github/` and is not
active; nothing was added under `.github/` by this work. Every `uses:` is pinned to a commit SHA (section 11); re-check them before activation.

## 5. Reproducible build and check

From the repository root, with `LEGEND_CATALOG_CACHE` pointing at the catalogue cache (it is not tracked; the counts of the page do
not depend on it but the package build reads the catalogue):

```bash
python3 -B framework/scripts/repurposing_coverage.py run                      # only if the inputs changed
python3 -B framework/scripts/repurposing_view.py run --source shareable
python3 -B framework/scripts/repurposing_view.py package                      # writes the package and the table of section 4
python3 -B framework/scripts/repurposing_view.py package --check              # exit 1 if the folder or the table differs from a fresh build
python3 -B framework/scripts/repurposing_view.py package --zip PATH           # deterministic zip (fixed timestamps, sorted entries)
python3 -B framework/scripts/repurposing_view.py audit-shareable --dynamic    # the publication proof, must PASS
python3 -B scripts/public_release_gate.py                                     # the repository gate
```

## 8. Rollback

1. Stop serving: repository Settings, Pages, "Unpublish site" or disable the Pages source (the label of the control depends on the Pages source type and could not be checked offline), or delete the `github-pages` environment deployment. Effective within minutes;
   CDN caches may serve the page for a short time. Actions artefacts and the deployment history stay until deleted.
2. Remove the mechanism: delete `.github/workflows/<copy of the proposal>` in a commit (or `git revert` the commit that added it). The
   proposal file under `view/` can stay; it does nothing there.
3. For route B: delete the release asset and, if wished, the release.
4. Revert any generator wording change of section 6 with `git revert` and regenerate.
5. What a rollback cannot do: recall copies a third party already made, or edit history. Those belong to the reserved decision below.

## 12. Languages (English initial; Italian, French, Spanish, German)

The shareable package holds five renderings of one dataset: `index.html` (English, the initial language) and `it.html`, `fr.html`, `es.html`, `de.html`. They are produced by the same generator (`repurposing_view.py run --source shareable`, no `--lang` = all five) from one set of data; only the wording differs. The wording lives apart from the data: interface texts in `view/i18n/ui_<lang>.json` (key `<table>.<key>`, the Italian text tables of the generator stay the source), curated reader-facing passages (rationale, counter-evidence, uncertainty) in `view/i18n/content_<lang>.json` keyed by the hash of their original; `ui_source.json` and `content_source.json` list what must be translated (`repurposing_view.py i18n --what collect`), and `i18n --what check` refuses an incomplete interface file or a translation that changes a placeholder, an identifier or a number.
A passage with no translation, or whose original changed since it was translated, is shown in its original language with an `EN` or `IT` marker, never silently; the technical sections (full matrix, filters, need cards, registries) are in English only and say so on every other page. The selector at the top is five ordinary links (they work without script and by keyboard, 44 px targets on a phone); a few lines of script remember the choice in `localStorage` (wrapped: it can be absent) and let only the English page open the remembered language; the filter hash is carried across.
Verification before a change of wording is published: `i18n --what check`, `test_repurposing_view_i18n.py`, the static audit of every page, `audit-shareable --dynamic`, `viewports` for each page, and an independent reading of the high-risk passages (negations, hedges, unknown versus negative) in each language. The translations were produced by language models and then read by separate reviewers; they are not certified human translations, and a medical or regulatory use needs a human review.
