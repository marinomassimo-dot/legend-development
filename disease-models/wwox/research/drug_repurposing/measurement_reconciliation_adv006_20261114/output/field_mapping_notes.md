# Field mapping for a possible `DESIGN_MAP` registration (ADV-006; input for HE, not a wiring)

## What a mapping entry is made of (read from the two existing entries)
`DESIGN_MAP[package][table] = dict(step=[cols], precondition=[cols], controls=[cols], outcomes=[cols], decision=[cols], scope=[cols], link=[cols])`. Seven slots, each a list of column names (an empty list renders "absent"); `design_rows()` copies cells verbatim under the slot name with "not stated by the package (no such column)" or "(empty cell)", lists unmapped non-empty cells, and states that a design has no observation. The key is the package table's first design column, and the row id is `package::table::key`. The package must be registered in `hypothesis_packages.tsv` (columns package, dir, role `design_only`, inv_id, why): one investigation per registration. The existing entries: `isrib_discrim_20261108` (table `design.tsv`: step=question, arms, readouts; precondition=condition_on; controls; outcomes=if_result_X_then; decision) and `myelin_generative_it36_20261108/levers_bc` (table `experiments.tsv`: step, controls from three columns, outcomes=weakened_by, scope from two, link=hyp_id).

## How this thread differs
1. **The reader only opens three file names**: `DESIGN_TABLES = {"design.tsv": "step", "grid.tsv": "pattern_id", "experiments.tsv": "exp_id"}` (`hypothesis_package.py` line 72). None of the thread's tables is so named (`new_measurements.tsv` key meas_id, `levers.tsv` key lever_id, `matrix.tsv` key obs_id, `reopen_searches_it14_p3.tsv` key id): the reader's table list is a code change, not a mapping.
2. **The existing tables have dedicated columns for the slots; these have fewer.** SCI42 `new_measurements.tsv` has one free-text `measurement` cell holding preparation, mode, quantity and conditions together (no separate columns) and no decision and no outcome column. SCI47 `levers.tsv` and `matrix.tsv` have outcome and decision-like columns but no precondition column (the condition sits inside `status`). IT14's table has no controls, outcomes or precondition.
3. **`conditional_prediction.tsv` has no unique key.** `expl_id` repeats (two manipulations per explanation); the reader keeps the later row of a duplicate key (and `check` reports it), so a composite key would be needed.
4. **`explanations.tsv` is a hypothesis table**, not a design; the explanation ids are not hypothesis ids of any registered package.
5. **Different meanings in the same-named slot:** `required_from_start` (a need, with a condition on another row) is not "unmet until the step before is run"; `status` embeds conditions; `separates` is not a possible outcome; `adds_over_general_anticonvulsant_action` is not the decision a result changes.
6. **Same measurement, several tables.** The seven recording steps of SCI47's Phase 0 exist only as prose in `design_review.md`; the same recordings reappear as SCI42's M01-M06 and as matrix `discriminating_measure` cells. A registration of all tables would produce several design rows for one recording (the generator has no cross-package reconciliation); `measurements.tsv` of this folder is the reconciliation, and it is not a table the reader knows.
7. **`inv_id`:** the packages do not state one investigation for the thread (ADV-004 `consumer_delta.md` row 5 mentions INV-10 and INV-05 for generated views); a registration needs that decided by the owners.

## What a registration would need (HE's decision, not made here)

One generic mapping cannot cover the four: the slot columns differ per table (`field_mapping.tsv`).
