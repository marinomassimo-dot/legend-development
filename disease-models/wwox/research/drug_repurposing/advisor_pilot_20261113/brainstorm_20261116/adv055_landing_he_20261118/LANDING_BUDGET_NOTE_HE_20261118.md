# ADV-055: the landing pipeline's time budget, measured (HE, 2026-11-18)

Written for: ADV (host) and, as a design note, the operator. Zero spend; read-only on logs, locks and refs; nothing in the gate or in `safe_push.py` was changed. Labels: MEASURED (from the files named), ESTIMATED (stated assumption), ASSUMED.

## Answer first
**What a landing holds the lock for is almost entirely the gate's per-file privacy scan, repeated over the whole repository for a commit that changes three files.** Median hold after the lock 3.5 minutes; 80% of the gate's runtime is `scan_privacy_and_secrets`; a landing changes a median of 3 of 12,234 tracked files (0.025%), so more than 99.9% of the work re-checks inputs that did not change. Waiting is the visible cost: since 2026-11-17, 130 serialized landings waited 9.4 hours in total (median 2.8 to 4.0 minutes, 41 to 43% longer than 5 minutes, p90 about 10 minutes), more than the 7.8 hours the lock was held. I recommend one change (a per-file result cache), as a design note because it changes when a scan may be skipped; I did not implement it. Two cheaper observations are free.

* **Queue length (MEASURED, serialized logs):** at least one publisher waiting or holding for 33 to 36% of 11-17 and 11-18; at least two for 13 to 17%; at least three for 3 to 5%; four at the most. Arrivals are bursty (up to 10 landings in an hour at 21:00 to 23:00 on 11-17, none or one in other hours), which is why a lock held for about a quarter of the day still produces waits above five minutes in four landings out of ten.
* **Not serialized (older tool copy or a plain gate run):** 12 to 49 landings a day, run time median 6.7 to 8.2 minutes against 3.5 to 3.6 for serialized. They run beside the lock holder, on 4 cores that already carry load average 4.7 (MEASURED `uptime`). The documented practice is `--serialize`; the 2-to-1 difference is the cost of not following it, and some part of it falls on the holder.
* The hold splits into merge, gate and push; the logs do not time them separately. The gate is the whole `scripts/public_release_gate.py` in its default staging mode (`safe_push.py` line 229 runs it with no arguments): four scans, no suites and no clean clone (those run only in release or clone mode).

## 2. Where the gate's time goes and how much of it re-checks unchanged inputs
Stage times (MEASURED, one instrumented pass of the four stage functions on the current tree, 12,234 tracked files, while the machine carried load 4.7; the sum, 275 s, is above the typical logged hold of 210 s for that reason; proportions are what to use; `gate_stage_times.py`):
| Stage | seconds | share | Depends on |
|---|---|---|---|
| `scan_privacy_and_secrets` | 218.7 | 79.5% | each file's own text and path (per file) |
| `scan_readme_consistency` | 30.0 | 10.9% | all Python files and the README (cross-file) |
| `scan_links` | 23.5 | 8.5% | all Markdown files and a name index (cross-file) |
| `scan_provenance` | 2.7 | 1.0% | declared data patterns against files (cross-file) |
* **Per-file purity of the 80% (MEASURED, `privacy_shard_purity.py`):** the full privacy scan took 254.9 s and gave 31 findings (all REVIEW, none BLOCK: the tree passes); the same scan restricted to 1,515 files (a random 1,500 plus all 19 files that carry a finding) took 34.8 s and gave findings identical to the full run's for those files, none outside them. About 23 ms a file. The pre-check of ADV-041 reproduced the two real refusals of 11-17 (a CLINICAL_CASE_LINKAGE line in a TSV and a BROKEN_MARKDOWN_LINK) on the named files only. **Not proved here:** equality on the gate's own BLOCK fixtures (`scripts/test_public_release_gate.py`), which is the protocol below.
* **Share of work on unchanged input (MEASURED):** 290 non-merge commits since 11-17 changed a median of 3 files (p90 9, max 33), 0.025% of the tracked files; 220 of them (76%) touch only records (disease-models, ledger, reviews, learning, files) and no Python; 70 touch code, framework, governance, scripts or `.claude`. A landing therefore re-runs the privacy scan on more than 99.9% unchanged files and, for the 76% records-only commits, the three cross-file stages as well.

## 3. Options, ranked by the waiting they remove (ESTIMATED; the log-based queue replay did not reproduce the observed waits, so I scale the observed waits by the new hold instead: new wait <= observed wait x (new hold / old hold), an upper bound because shorter busy periods also shorten queues; overhead of fetch, merge and push ASSUMED 20 s)
| # | Option | Hold per landing | Waits (median / p90 of today's 2.8 / 10.1) | Exact risk to what the gate verifies |
|---|---|---|---|---|
| 1 | **Per-file privacy result cache** keyed by sha256(gate script bytes) + file blob id + path + the exempt-set digest, stored next to the lock; cache hit = the stored findings, miss = scan | about 1.0 min (cross-file stages 56 s of 275 plus overhead, privacy about 0) | about 0.8 / 3 min | Memoises a function shown pure on 1,515 files; **a changed gate script changes every key, so a detector tightening is applied to the whole tree at once** (the one way a cache could differ from today); risks: a key that omits an input the scan reads (path-dependent exemptions, `unpublishable_paths`), a corrupt cache file (a bad entry would hide a finding); mitigations: key includes the script digest, a full uncached run on demand and at least daily, `--no-cache`, fail closed (any cache error = scan) |
| 2 | **Gate the exact SHA's per-file stage before the lock; under the lock merge, rescan only files changed on both sides, run the cross-file stages, and run everything if the gate script changed in the merge** | about 1.0 min | about 0.8 / 3 min | No persistent state; per-file stage relies on the clean-merge argument (a merged blob is either the author's or main's, each scanned, unless both changed it); more CPU outside the lock on 4 loaded cores (gates run in parallel), so a landing's own latency falls less than the lock hold; same detector-change rule as option 1 |
| 3 | Records-only fast path with declared path rules (skip the cross-file stages and part of the scans) | about 0.4 min | about 0.4 / 1.5 min | **Changes WHAT is checked, and the 11-17 refusals were records-only commits** (a Markdown link, a TSV line): the links and case-linkage checks are exactly what a records-only commit can break. Not recommended |
| 4 | Coalescing small landings (one gate for several) | per landing about 1.0 to 2.0 min | about 1.5 / 5 min | needs a coordinator; a refusal blocks several landings; no gate change |
| 5 | Leave as is, and have every session use `--serialize` | 3.5 min | 2.8 / 10.1 | none; removes the not-serialized 7-minute runs |
Per-landing latency from intent to published (median, ESTIMATED): now about 7.5 minutes (observed), option 1 about 2.2, option 2 about 4.7 (the pre-lock scan stays on the path), option 3 about 1.0.

## Recommendation
**Option 1, as a design note, with this proof protocol before any code lands** (verdict identical for every input the current gate fails on): (a) on the current tree, cached run twice (cold, warm) against the uncached gate: byte-identical findings; (b) on every failing and passing fixture of `scripts/test_public_release_gate.py` (66 tests, including CLINICAL_CASE_LINKAGE, broken links, provenance and README consistency): same verdict and same findings with an empty cache, with a warm cache, and after editing one file; (c) a gate-script edit invalidates all entries (test); (d) a corrupted cache file yields a full scan, not a pass (test); (e) `--no-cache` and an environment switch restore today's behaviour exactly (the reversal). It saves about 2.5 minutes of every landing's lock hold and, by the scaling above, 60 to 70% of the waiting; it also cuts the CPU the whole machine spends on gates by about 80%, which helps the not-serialized runs too. Needs the operator's and ADV's decision because it is a privacy control that would stop re-reading unchanged files. Meanwhile, option 5 costs nothing: use `--serialize` in every recall and brief (35% of the logged landings on 11-17 were not serialized and ran twice as long). If you judge 4 minutes a landing not worth a change, the numbers above are the cost of leaving it: about 9 session-hours of waiting in two days, during which a session may not commit or edit its worktree.

## Limits
Logs are partial and one reused log distorts one 11-16 value; the replay model did not reproduce observed waits (it saw none), so the saving figures scale observed waits and are upper bounds on the new waiting; stage times were taken under load 4.7 once, not repeated; overhead of merge and push is assumed; the gate's verdict identity on its BLOCK fixtures was not tested here; I did not read the gate's per-file loop line by line for hidden cross-file state beyond the two differential tests; no change was made to the gate or the lock.
