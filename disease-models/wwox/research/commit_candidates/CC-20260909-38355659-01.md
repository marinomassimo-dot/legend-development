## 4 · 🔴 A blocking defect in `erratum_scope_check.py` — reported, deliberately not fixed

**Applying §2 to `PMID38182577.json` will crash the tool.** So will this reading's own manifest,
which already declares the empty scope honestly.

```
File "framework/scripts/erratum_scope_check.py", line 197, in check_manifest
    "locators": len(entries),
UnboundLocalError: cannot access local variable 'entries' where it is not associated with a value
```

**Cause.** The `declared is not None and not declared` branch returns `len(entries)` **one line
before `entries` is assigned**:

```python
    declared = rc.get("corrected_items")
    if declared is not None and not declared:
        return {..., "locators": len(entries), ...}      # <-- entries not yet bound
    entries = ((data.get("verbatim_locators") or {}).get("entries")) or []
```

**Why it survived review.** The branch had never executed — **no manifest in the corpus declared an
empty scope until today**. The 12/12 self-test cannot see it: it exercises `parse_panel` and
`intersects` and **never calls `check_manifest`**.

**Blast radius, measured.** Corpus-wide runs crash; `--pmid`-targeted runs still work; the
self-test still reports 12/12 green, which is the part that makes this worth flagging loudly — the
tool's own green light does not cover its own crash.

**The one-line repair** (move the assignment above the branch):

```python
    entries = ((data.get("verbatim_locators") or {}).get("entries")) or []
    declared = rc.get("corrected_items")
    if declared is not None and not declared:
        return {...}
```

**And the regression that would have caught it**, which is the part worth keeping: a case that
calls `check_manifest` on a fixture whose `retraction_check` affirms an erratum and declares
`corrected_items: []`, asserting `status == "CLEAR"`. Reproduced today against exactly such a
fixture.

**Not fixed by this actor.** `framework/scripts/erratum_scope_check.py` is a peer's file
(`ce7f89a`, `scientist-b`) and cross-actor fixes are the orchestrator's under this task's dispatch.
Reported here rather than repaired, and recorded under `DEFAULTS_TAKEN`.
