# Decision 1 — D.2 scoped ruling

## Question

UNRESOLVED-A (REV-ORCHSURF-ADD-002-PATCH-SPECIFICATION.md §8):

May the MIRROR_REVIEW representation directed by
CLOSE-REV-ORCHSURF-MIRROR-002-ADD-002 be used for this specific case without
amending Annex D.2?

## Ruling

For this specific case only:

The `MIRROR_REVIEW` field of:

`CAND-20260819-ORCHSURF`
revision 4 candidate manifest
locus L-2 identified by `CLOSE-REV-ORCHSURF-MIRROR-002-ADD-002`

may carry the directed representation required by:

`CLOSE-REV-ORCHSURF-MIRROR-002-ADD-002`.

The bytes of the directed representation are those specified by
CLOSE-REV-ORCHSURF-MIRROR-002-ADD-002 §4, as transcribed via
REV-ORCHSURF-ADD-002-PATCH-SPECIFICATION at the revision selected in
Decision 4. This decision does not restate them and adds no wording of its
own.

## Rationale

The existing D.2 vocabulary remains unchanged.

The case represents a documented exceptional state generated by a closed
review process: a review occurred, its outcome is not PASS, and it concerns a
revision path that the enumeration `n/a | PASS | FAIL + REVIEW_ID` cannot
represent truthfully.

The ruling does not authorize a review to carry a new name; it authorizes
that specific candidate manifest field to represent that specific true state.

## Non-generalization constraint

This ruling does not adopt any general interpretation of Annex D.2.

This ruling applies only to the field and locus identified above, as directed
by CLOSE-REV-ORCHSURF-MIRROR-002-ADD-002.

No actor may cite this decision as establishing a general extension of the
D.2 vocabulary.

The case is recorded as evidence for a possible future governed D.2
amendment process.

If equivalent cases recur, the appropriate response is a governed schema
review.

One scoped ruling is an exception.

Repeated scoped rulings indicate a possible schema design issue.

# Decision 3 — Working surface and binding

## Question

UNRESOLVED-C (REV-ORCHSURF-ADD-002-PATCH-SPECIFICATION.md §8):

Where does the authorized transcription land before canonicalization?

## Ruling

The transcription must be performed on the transcribing actor's working
branch. For candidate modification the transcribing actor is Plan
(Decision 2).

No ref named `plan` exists at the date of this decision. The working
branch is created or identified, and pinned, in the transcription dispatch
binding. Its creation or identification is part of that dispatch, not of
this decision.

This designation is an operator act. It deliberately selects a surface
class — the transcribing actor's working branch — distinct from the two
surfaces enumerated at the question's source.

The transcription applies only to the pinned candidate text identified in
the transcription dispatch.

Before application:

- the responsible branch tip must be recorded;
- the exact candidate blob must be recorded;
- the three authorized loci must be re-derived on that pinned baseline;
- no locus may be inherited from CONTENT_TIP unless independently verified
  on the transcription surface.

CONTENT_TIP identifies the reviewed object identity.

CONTENT_TIP does not define the writable transcription surface.

The writable surface is determined by the transcribing actor's branch and
the explicit transcription dispatch binding.

The resulting state must receive a new explicit binding before any canonical
batch operation.

## Referents

In this decision:

- "the transcription dispatch" is the future governed dispatch that tasks
  Plan with the transcription. It does not exist yet, and it is not created
  or authorized by this decision.
- "the three authorized loci" are the loci L-1, L-2 and L-3 identified by
  CLOSE-REV-ORCHSURF-MIRROR-002-ADD-002 §4.
- UNRESOLVED-A, -B, -C and -D are defined at
  REV-ORCHSURF-ADD-002-PATCH-SPECIFICATION.md §8, read at the revision
  selected in Decision 4.

## Constraints

main is not a working surface.

main changes only through canonical batch procedures.

A branch tip movement is expected and legitimate when recorded explicitly.

No implicit rebinding is permitted.

# Ratification integrity

Hash convention: SHA-256 (`shasum -a 256`) is the binding convention for
pre- and post-ratification hashes. Git object hashes are supplementary
identifiers only.

## Hashed states, defined

PRE state: `ratified_by` empty, `pre_ratification_hash.value` empty,
`post_ratification_hash.value` empty.

`pre_ratification_hash.value` is the SHA-256 of this document in PRE
state. After computation, the value is written into the frontmatter; the
in-file copy is declarative. A verifier reproduces it by emptying the
three fields above in a working copy and recomputing.

POST state: `ratified_by` filled, `pre_ratification_hash.value` filled,
`post_ratification_hash.value` empty.

The post-ratification hash is the SHA-256 of this document in POST state.
It is never written into this file: the frontmatter field exists to
declare the algorithm and remains empty by design. The value is
registered externally by Plan at registration time, so that verification
has a stable object.

The only differences between PRE state and POST state are exactly two:
`pre_ratification_hash.value` and `ratified_by`. If anything else
differs, stop: any material modification after ratification requires a
new review.
