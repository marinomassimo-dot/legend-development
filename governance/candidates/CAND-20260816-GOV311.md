### How the hash is defined

`plan_defined_parameters.md` § P5 defines the hash over a git tree oid. Revision 1 applied it by
**hand-picking the commit before the manifest's own**, to dodge the self-reference — which worked
but was a judgement embedded in prose, exactly the thing the repository's own rules say decays.
Revision 2 replaces the hand-picked commit with a deterministic filter (PID-06, amended):

```
CANDIDATE_CONTENT_HASH = SHA-256(
    "legend-candidate-v2\n" + <base-head> + "\n" + <filtered tree listing>
)

filtered tree listing = `git ls-tree -r --full-tree <tip>`, excluding every path under
                        governance/candidates/
```

Reproduce it with:

```bash
git ls-tree -r --full-tree 1c755e59 | grep -v $'\tgovernance/candidates/' \
  | { printf 'legend-candidate-v2\n749a9a9b8f29c855f803a43b979c591532557561\n'; cat; } \
  | shasum -a 256
```

506 tree entries are hashed. The property this buys: **editing this manifest never changes the
hash of the content it describes, and editing any content file always does.** A manifest
containing a hash of a tree containing that manifest is a fixed point; excluding the manifest
directory by rule, rather than by choosing a commit, resolves it without anyone having to
remember which commit was picked and why.

The version prefix moves from `v1` to `v2` so the two definitions can never produce colliding
values.
