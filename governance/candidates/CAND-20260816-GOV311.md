### How the hash is defined — by reference, not here

**The single authoritative definition is
[`plan_defined_parameters.md` § P5](../plan_defined_parameters.md).** This manifest references
it; it does not restate it. That is the repair for RC-2, where a `v1` definition in P5 and a `v2`
recipe in the manifest disagreed while PID-06 named P5 as the implementation site.

`CONTENT_DOMAIN_DEFINITION` (P5.1, in one line): every path in the tree at `BRANCH_TIP` **except**
paths under a declared control-plane root — today `governance/candidates/` and `ledger/`. Content
is what is proposed for canonical integration and determines the candidate's identity; the
control plane is what *describes or manages* a candidate, a review or an actor's runtime state,
and cannot change the identity of what it describes.

`REPRODUCTION_COMMAND` — one command, from the repository root:

```bash
python3 governance/scripts/candidate_content_hash.py \
  --base 749a9a9b8f29c855f803a43b979c591532557561 \
  --tip  9720a0cd1dddfe457f8e4eec1ebe47bd627512cc --show-domain
```

It prints the version, base, tip, included entry count and **every excluded path**, then the
hash. The count is derived by the same pass that builds the value (RC-3), so it cannot go stale
beside it, and the excluded set is visible rather than trusted.

The script does not carry its own copy of the rule: it parses `CANDIDATE_HASH_VERSION` and
`CONTROL_PLANE_ROOTS` out of § P5, the same anti-drift shape as `governance_fingerprint.py`
(PID-03). Nothing passes through a shell — the revision-4 defect was `$(...)` stripping one
trailing newline.

The version prefix moves to `v3` because both the byte layout and the excluded roots changed, so
`v1` and `v2` values can never collide with these.
