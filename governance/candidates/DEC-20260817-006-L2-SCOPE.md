## 5 · The finding — and here the provenance changes mid-paragraph

**The run's most valuable output is its failure, not its pass.** S3a — the naive copy-over
strategy — left contamination. `BY-REPORT (ORCH)`

**And the shipped implementation is the naive copy-over.** `PRIMARY (PLAN)` — Plan read
`framework/scripts/batch_commit.py` directly, independently of the relay:

```python
def restore(snapshot_dir, repo_root):
    for rel in CURRENTS + EXTRA:          # a FIXED list
        src = os.path.join(snapshot_dir, rel)
        if os.path.isfile(src):           # silently skips what the snapshot missed
            dst = os.path.join(repo_root, rel)
            os.makedirs(os.path.dirname(dst), exist_ok=True)
            shutil.copy2(src, dst)        # copies; removes nothing
```

It iterates a fixed list, copies each file present in the snapshot, and **removes nothing**.
It cannot delete a stray file because it never enumerates the destination tree.

**So S3a is not a hypothetical alternative that lost a comparison. It is the behaviour in
this repository today** — and that half of the claim is Plan's own reading, not a relay.

**🔴 The `GATE 4` consequence, which precedes any batch.** `GATE 4`'s restore path is the
mechanism relied on when a batch fails. If restore leaves contamination from files it does
not enumerate, a failed batch does not return the tree to its prior state — it returns the
known files and leaves the unknown ones. That is a property of the recovery mechanism for
**every future batch**, and it was found by a test costing one scratch directory.

**The day's signature, a fifth time.** `restore()`'s docstring says *"copy current/state
files from a snapshot"*, and it does exactly that, correctly. What is wrong is the noun
attached downstream: `BATCH_COMMIT` treats it as *restore*, meaning *return the tree to its
pre-batch state*. Two different contracts; only the narrower is implemented. Measured
correctly, labelled wrong — after bytes vs characters (834/829), zero- vs one-based
(469/470), pipe lines vs body rows (13/12), and Plan's own *"wrong tree"* for a tree that
was equivalent in the only domain deciding identity.

## 5e · What the repair must actually do — widening the list is not enough

`PRIMARY (PLAN)` — re-read at source, all three parts confirmed.

**Two independent failure paths, not one.**

```python
for rel in CURRENTS + EXTRA:
    if os.path.isfile(src):        # 2 · a listed file absent on disk is SILENTLY SKIPPED
        shutil.copy2(src, dst)
...
snapshot(args.repo_root, args.dest)
print(f"Snapshot written to {args.dest}")
return 0                            # unconditional success, always
```

1. the list enumerates 5 where Phase 3 names 9 patterns
2. **within those 5, a missing file is skipped without a word**

**Widening the list repairs only the first.** Extend `CURRENTS + EXTRA` to all nine patterns
and `if os.path.isfile(src)` still swallows any absent file and still returns 0. A snapshot
missing a registry — the case Phase 3's `ABORT` is most obviously written for — would print
*"Snapshot written to …"* and exit clean.

**So the repair is:** enumerate the required set, verify every member landed, fail loudly
otherwise. That is `PATTERN_ALREADY_SOLVED_GATE`'s own durable form — *the test mounts the
condition itself, plus a companion assertion that the fixture would have failed without the
fix* — applied to a gate rather than to a test.

**The asymmetry, confirmed verbatim.**

```python
restore_parser.add_argument("--confirm-restore", action="store_true",
    help="required acknowledgement because restore overwrites current files")
```

`restore` demands acknowledgement; `snapshot` demands nothing and validates nothing. **The
operation whose risk is visible carries a guard; the operation whose completeness is a gate
condition carries none** — and the second is the one that fails silently.

**🔴 Plan's addition: the asymmetry is real, and both commands share a deeper defect.**
`restore`'s exit is *also* unconditional — it prints *"Snapshot restored from …"* and returns
0 whether or not anything was restored. So `--confirm-restore` guards against **unintended
invocation**, never against **incomplete execution**. Those are different risks. The tool
addresses only the first, in only one of its two commands, and neither command can report
that it did less than it claimed.

Worth recording beside it: `restore`'s `--repo-root` defaults to `"."`. Invoked from the root
with `--confirm-restore`, it overwrites the live current files, and that flag is the only
thing standing between the command and them.

**On the two instances of the same class.** The Orchestrator refused an unperturbed restore
test because a check that cannot fail is worthless — while the tool it would have tested had
been running that exact defect in production for eleven days. Its own note is the right one
to keep: *"I caught it where I was asked to look and not where it was already live. That is
not a point in my favour; it is the argument for the gate being mechanical, since attention
found the hypothetical and missed the actual."*
